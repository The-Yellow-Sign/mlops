# Способы организации GitLab полигона

**Вариант A** - публичная группа (например, [вот](https://gitlab.com/soafee))
Плюсы:
- Нет необходимости разворачивать и настраивать гитлаб локально;
- Данные публичны, можно сразу тестировать извлечение через API;
- Быстрый старт.
Минусы:
- Контроль над инфраструктурой ограничен: доступы/роли, создание тестовых проектов;
- Не настраиваемые ограничения со стороны GitLab API;
- Вебхуки только для owner и maintainer.

**Вариант B** - локальный GitLab (например, Docker)
Плюсы:
- Полный контроль: структура групп и проектов, доступы/роли;
- Пользовательские настройки ограничения API;
- Настройка вебхуков
Минусы:
- Развертывание и настройка;
- Отсутствие готовых групп и проектов.

**Вариант C** - гибридный (**A** + **B**)
Плюсы:
- Полный контроль (локальный) и разнообразные сценарии (публичный);
- Сначала тест на локальном, затем дополнительно на публичном;
- Гибкий подход к отработке разных сценариев: доступ к публичным проектам, настройка публичного GitLab API и локального.
Минусы:
- Требует больше усилий, чем использовать только локальный или публичный GitLab;
- Развертывание и настройка локального GitLab.

**Вариант D** - публичная группа (своя)
Плюсы:
- Нет необходимости разворачивать и настраивать гитлаб локально;
- Данные публичны, можно сразу тестировать извлечение через API;
- Полный контроль: структура групп и проектов, доступы/роли;
- Настройка вебхуков.
Минусы:
- Не настраиваемые ограничения со стороны GitLab API;
- Отсутствие готовых групп и проектов.
# Вывод

Если выбрать вариант B, то придется каждому развертывать у себя локально гитлаб. Возникает вопрос: "Как будут предстоять дела с репами?". Сервера нет, а изменения какие-либо в гитлабе не будут синхронизированы.
Из-за чего, я создал приватный [GItLab](https://gitlab.com/the-yellow-sign-test). Решил, что лучше будет синхронность изменений, но ограничения, чем проблемы с синхронностью, но с полным доступом.

Некоторые ограничения бесплатной версии:
1. *Webhooks* только в платной версии
2. *Group access tokens* только в платной версии ([doc issue](https://gitlab.com/gitlab-org/gitlab/-/issues/442671))

Таким, образом, работаем в публичном GitLab через приватный *group*, используя [personal private token](https://docs.gitlab.com/user/profile/personal_access_tokens/). Основной акцент будет на публичный GitLab (free), но при реализации функционала будет акцент и на self-hosted gitlab, развернутый через Docker-compose. Поскольку, в описании проекта написано `Система разворачивается локально и работает полностью на стороне держателя Gitlab инфраструктуры`, нам необходимо и этот вариант учитывать. Так будет присутствовать универсальность использования как публичного GitLab, так и локального.
