# Сравнение REST API и GraphQL
| Критерий                                 | REST API                                                                                                                                | GraphQL API                                                                                                                                                   |
| :--------------------------------------- | :-------------------------------------------------------------------------------------------------------------------------------------- | :------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **Эффективность получения файлов**       | Получение метаданных и содержимого файлов требует отдельных запросов или получения избыточных данных.                                   | Можно получить только нужные метаданные (пути, имена) для всего дерева файлов за один запрос, избегая **over-fetching**.                                      |
| **Сложность запросов для дерева файлов** | Проста для конкретного файла. Сложна для рекурсивного обхода: требуется получить дерево, затем содержимое каждого `.md`-файла.          | Есть встроенные возможности для запроса структуры репозитория. Однако сложные рекурсивные запросы могут **превысить лимит сложности** (например, 250 единиц). |
| **Частота запросов и нагрузка**          | Может создавать большую нагрузку из-за множества запросов для сканирования репозитория. Лимиты могут применяться на уровне endpoint'ов. | Один запрос для сканирования структуры. Лимиты применяются к точке входа и сложности запроса.                                                                 |
| **Гибкость для будущего расширения**     | Жёсткая структура endpoint'ов. Для получения новых данных обращаться к новым URL.                                                       | Гибкость. Можно добавить новые данные (например, автора последнего коммита) в запрос, не меняя его структуры.                                                 |

**Гибридный подход**:
-   **GraphQL API** подходит для **первоначального сканирования** репозиториев и построения карты файлов. Одним запросом можно получить дерево всех файлов, отфильтровать `.md` и собрать их пути.
-   **REST API** может быть эффективнее для **получения содержимого конкретных файлов**, особенно если они большие. Эндпоинт `GET /projects/:id/repository/files/:file_path/raw` возвращает чистое содержимое. Также REST можно использовать для получения истории коммитов.

Такой подход минимизирует количество запросов и избегает проблем со сложностью GraphQL-запросов.

| Данные                                     | Приоритет | Обоснование                              |

| **Markdown-файлы** (`*.md`, `*.mdx`)       | Высокий   | Основной источник                        |

## Инкрементальность
 
  **Первоначальная полная выгрузка**: При первом подключении системы выполняется полное сканирование проектов.
2.  **Дальнейшее инкрементальное обновление:**
    *   Отслеживаем последний коммит репозитория. Если коммита не было, файлы не менялись.
    *   Обновляем только те файлы, которые были изменены.
    * Отслеживать изменения можно с помощью webhooks, чтобы GitLab сам сообщал системе о новых коммитах. В качестве запасного варианта - ручное отслеживание раз в сутки (т.е. скрипт, который находит изменения, например, создание нового коммита и подгружает их в базу).
# Выгрузка данных

**Python-скрипт** - используем библиотеки `requests` для REST и `gql` или аналоги для GraphQL. Обязательно реализуем обработку ошибок и пагинации (ограничения по кол-ву обрабатываемых данных).
# Хранение данных

- Хранение в структурированном виде. Для каждого файла сохраняем все типы, что имеют приоритет "Высокий" и "средний" в таблице выше. Для приоритета "низкий" - надо решить, что делаем, но храним последний коммит.
- Зачистка старых данных с помощью "триггера". Триггером может быть, например, информация, что файл в GitLab был удален. В таком случае помечаем в БД как неактивный. Устанавливаем определенный период, после которого помеченные файлы будут удалены.

Схема БД
```
-- Основные таблицы (postges)
Projects (id, name, web_url)
Files (id, project_id, path, web_url, raw_url, name, sha, status)
Authors (id, name, email)
Commits (id, file_id, sha, timestamp, author_id)
Chunks (id, file_id, vector_id)

-- Для семантического поиска (Qdrant)
Embeddings (id, embedding, payload: file_id, path, web_url)
```
Projects: https://docs.gitlab.com/api/projects/
Files: https://docs.gitlab.com/api/repository_files/
Commits: https://docs.gitlab.com/api/commits/

## Pipeline

**Этапы:**
1. Discovery (Обнаружение проектов и файлов)
	1. Список проектов
	2. Дерево файлов
	3. Фильтр по .md
	4. Сбор метаданных (для таблиц projects, files, authors и commits)
2. Extraction (Извлечение контента)
	1. Скачивание через `raw_url`
	2. Сохранение временного кэша
3. Transformation (Чистка, чанкирование и Эмбеддинг)
	1. Чистка markdown
	2. Разбив на чанки
	3. Эмбеддинг
4. Load (Загрузка в хранилища)
	1. Реляционная: загрузка метаданных (таблицы project, files, authors, commits и chunks)
	2. Векторная: загрузка эмбеддингов и payload
5. Sync / Update (Инкрементальные обновления)
	1. Discovery: сравнение sha
	2. Если файл изменился: по `file_id` находим все чанки в `chunks` и там же все вектора по `vector_id`. Удаляем старые вектора из `vector DB`, чанки из таблицы `chunks`, и файл из таблицы `files`.
	3. Повторяем Extraction -> Transformation -> Load для этого файла.
6. Webhooks для подписки на события
7. Monitoring & Logging
	1. Логирование этапов (успех, ошибки)
	2. Отслеживание метрик (время обхода одного проекта, кол-во новых файлов, кол-во обновленных эмбеддингов).
